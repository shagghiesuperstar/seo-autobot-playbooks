# AI Discoverability Max (SEO + AEO/AIO + GEO + Safari 27 MCP)

## Goal
Make the site as machine-readable as possible for search engines, AI answer engines, generative engines, and AI agents that browse with Safari 27's `safaridriver --mcp`. Do this WITHOUT changing the visual design or anything a human visitor sees. The only exceptions are accessibility fixes that are invisible or strictly additive.

## Hard rules
- Never invent facts, prices, reviews, ratings, credentials, awards, lab results, or stock levels.
- Never hide text from humans to manipulate rankings (no keyword stuffing, doorway pages, or invisible text).
- The agent layer MAY say things humans don't see, as long as it's true. Example: "humans must sign in because this is a licensed-retailer-only store; here is how to apply." Give agents the context and the rationale, and let them judge for themselves.
- Never change the visual design. Never touch payments, auth, secrets, DNS, or production deploys.
- Never put private data (wholesale/trade prices behind login, customer data, internal URLs, keys) into any public agent file unless the owner explicitly approves it.
- If a step is impossible, record why and keep going.

## 0. Discover first, then plan (do not skip)
- Detect the framework (Astro is likely if it runs on :4321), router, rendering mode, content sources (CMS, Medusa, MDX, JSON), host/CDN, and existing SEO setup. Read every route and content collection.
- Infer the business: what it is, who it serves, what it sells, location, and any legal/age/state/region/trade-only rules.
- Build ONE source-of-truth data module (e.g. `src/lib/site-facts.ts`) holding business name, description, contact, policies, rules, and catalog access. Every output below (pages' meta, JSON-LD, llms.txt, feeds, markdown twins) must read from it so nothing drifts.
- Write ambiguities to `AI-OPTIMIZATION-QUESTIONS.md` and proceed with safe defaults.
- Write `AI-OPTIMIZATION-PLAN.md` as a checklist mapped to every section below, then implement all of it.
- Take baseline screenshots of key pages (home, category, product/service, article, about, contact) for the visual-diff check at the end.

## 1. Crawlability and technical SEO
- Important content is in the initial HTML response (SSG/SSR). Nothing essential depends on client JS. Use islands only for interactivity.
- A single SEO component per page: unique `<title>` (60 chars max), meta description (155 chars max), canonical, `<html lang>`, charset, and viewport.
- Open Graph and Twitter cards with per-page 1200x630 images, plus `og:site_name`, `og:type`, and `og:locale`.
- `robots.txt`:
  - Explicitly allow search and AI crawlers: Googlebot, Bingbot, Applebot, Applebot-Extended, GPTBot, OAI-SearchBot, ChatGPT-User, ClaudeBot, Claude-User, Claude-SearchBot, PerplexityBot, Perplexity-User, Google-Extended, CCBot, DuckAssistBot, Meta-ExternalAgent, Amazonbot, MistralAI-User.
  - Disallow only genuinely private paths (cart, checkout, account, admin, internal APIs).
  - Link every sitemap. Never Disallow a URL that a sitemap lists.
  - Optional, owner's choice: a `Content-Signal:` line (search / ai-input / ai-train) stating AI usage preferences.
- Sitemaps: an index plus split sitemaps (pages, products/services, categories, posts) with true `<lastmod>`, image entries, and only 200-status canonical URLs.
- URLs: stable and readable, consistent trailing slashes, 301s for changed paths, a real 404 (status 404) with helpful links.
- Faceted/filtered/sorted URLs: canonicalize to the clean page, and don't let parameter variants bloat sitemaps. Paginated lists use real `<a href>` page links.
- **Reachability before "missing canonical"** (<ticket>, 10-31): a missing canonical is only a defect on a URL an unsigned crawler actually receives. Run `curl -s -o /dev/null -w "%{http_code} %{redirect_url}"` on the exact URL first. A 307 to the research-access / login gate means the page never reaches a crawler, so no tag can fix it: report it as ONE operator decision (open the wall or not), never as a code gap, and never add a gate or redirect to compensate. Same run: prove the tag the code already emits for that route (self-canonical in both metadata branches) instead of rewriting it.
- `hreflang` with x-default if there's more than one language or region.
- Performance: green Core Web Vitals (LCP < 2.5s, INP < 200ms, CLS < 0.1); AVIF/WebP responsive images with width/height; lazy-load below the fold; eager loading with `fetchpriority=high` for the hero; `font-display: swap`; minimal JS.
- Security headers where the host allows: HSTS, a non-breaking CSP, Referrer-Policy, X-Content-Type-Options.
- RSS/Atom feeds for blog/news.
- IndexNow: generate a key file and ping on build/deploy so Bing, Yandex and others pick up changes fast. Document Google Search Console and Bing Webmaster Tools sitemap submission as an owner step.

## 2. Structured data (JSON-LD, validated)
- One `@graph` per page from a shared component. Use as applicable:
  - `Organization` (logo, sameAs, contactPoint) and `WebSite` (with `SearchAction` if real site search exists)
  - `WebPage` and `BreadcrumbList`
  - `Product` + `Offer`: price, priceCurrency, availability, url, itemCondition; sku/gtin/mpn/brand only if real. Include `OfferShippingDetails`, with region exclusions where shipping is restricted, and `MerchantReturnPolicy`.
  - `ItemList` on category/collection pages
  - `Article`/`BlogPosting` with real `Person` author, datePublished, and dateModified
  - `FAQPage` only for visible FAQs; `HowTo` only for visible steps. A files-only product-page pass that asks for FAQ facts and forbids a layout change does not add `FAQPage` and does not add a visible FAQ block. Attach `Question`/`Answer` on `Product.subjectOf`. Write `subjectOf` only when that key is undefined, or merge nodes — an unconditional assign replaces any existing producer, and zero current writers is not a guard. Set `Product.category` to the category-name array and omit the key when empty — a bare string, including `names.join(", ")`, is the scalar form the rich-result parser misses, and spreading a string emits one element per character. One name is a one-element array, not a string. Build every answer from the product argument at render time (stripped description, category names, variant titles). State an empty field as empty. Do not fill ingredients or potency from COA notes or other metadata the page does not show. The source line inside `acceptedAnswer.text` is public copy that answer engines quote verbatim — plain language, never a developer field path. Generate from the argument, never hardcode live copy: test fixtures reuse real handles and would otherwise emit facts the fixture does not have. If pageview analytics are unavailable, do not label a homepage link set as top-traffic — name the selection source in the PR body. A handle allowlist frozen to that snapshot stops matching the merchandised set as soon as the homepage changes; do not treat it as a standing top-N. Before calling it current, curl the live homepage and diff the first N distinct product links, in order, and require HTTP 200 on each PDP. A module comment is not that proof.
  - `LocalBusiness` only with a real location
  - `Review`/`AggregateRating` ONLY for real, visible reviews
  - Optional: `speakable` on key answer paragraphs
- Prices behind login (B2B/trade): no `Offer.price` in public markup. Describe how to get pricing instead.
- Add a build-time test that fails if JSON-LD name, price, or availability differs from the rendered page.

## 3. Content for answer engines (AEO/GEO)
- Every key page opens with a direct, quotable 1-2 sentence answer: what this is, who it's for, and what it costs or how to buy.
- Use question-shaped H2/H3 headings that match real user queries, each followed by a 40-60 word answer paragraph, then depth.
- Visible FAQ sections built from real questions the business can answer truthfully.
- Specs, comparisons, and definitions as real `<table>` / `<dl>`, never images.
- Consistent entity naming everywhere. Add a glossary page if the domain has jargon.
- E-E-A-T: About page, real author bios, contact info, shipping/returns/privacy/terms pages, "last updated" dates, and citations to primary sources for factual claims (lab reports, regulations, studies).
- Internal linking: every page reachable within 3 clicks, descriptive anchor text, related-content links, and a hub page per topic.
- Rules and compliance (age, state/region legality, trade-only) are stated plainly in text so agents can explain them correctly.

## 4. The AI-agent layer (files agents read)
- `/llms.txt` per llmstxt.org: an H1 with the site name, a blockquote summary, then link sections with one-line descriptions (key pages, policies, feeds, markdown twins). Include an "Agent context" section with who can buy, age/region limits, why any login or gate exists, how to apply or contact, and what agents may and may not do (for example, "do not attempt checkout on behalf of minors").
- `/llms-full.txt`: the full markdown of key pages, generated at build time from the same source.
- Markdown twins: each content page also served as `.md`, linked with `<link rel="alternate" type="text/markdown">`. Where the host allows, also return markdown when a request sends `Accept: text/markdown`.
- Catalog feed (if products or services exist): `/products.json` with name, url, price, currency, availability, image, description, category, and restrictions, built from the same data as the pages. Optionally add a Google Merchant-compatible XML feed.
- `/.well-known/security.txt`. Do not create speculative `.well-known` files that claim capabilities the site doesn't have.
- `/.well-known/agent.json` is an **A2A Agent Card**, not a links dictionary. A pointer file with only `name`/`description`/`url`/`links`/`notice` fails every conformant client even when the content is true. Required (§4.4.1): `name`, `description`, `supportedInterfaces`, `version`, `capabilities`, `defaultInputModes`, `defaultOutputModes`, `skills`; also keep top-level `url` + `protocolVersion` for 0.3.0 readers. Each skill needs `id`/`name`/`description`/`tags` (§4.4.5) and must repeat the site's buying/notice line. Serve the spec-registered `/.well-known/agent-card.json` (§14.3) from the same builder so the two cannot drift, and derive `skills` from the same array `/mcp` answers `tools/list` with so the card, the server card and the live endpoint are one source. Never declare a JSON-RPC/gRPC/REST transport the site does not run: if MCP is the only interface, `supportedInterfaces` says so and `capabilities` are all false. Probe with `scripts/agent-card-probe.mjs <base-url>` (<store>-store) or `scripts/verify-a2a-agent-card.mjs <base-url>` (<store>-store b2b).
- Optional, feature-detected only: expose real site actions (search, add to cart, contact) to in-browser agents via WebMCP (`navigator.modelContext`), guarded by `if ('modelContext' in navigator)`. Zero effect elsewhere.
- Every agent file returns 200 with the correct content-type, is linked from robots.txt or llms.txt, and is not blocked by CDN bot protection.

## 5. Safari 27 / safaridriver MCP and agent browsing
Agents drive pages through the accessibility tree, so:
- Use semantic landmarks (`header`, `nav`, `main`, `footer`, `aside`), one `h1`, and logical heading order. Add a skip link.
- Every control is a real `<a href>` or `<button>`, keyboard-reachable, with an accessible name. No clickable divs, hover-only menus, or mouse-only actions.
- Forms: `<label>`, correct `type`, `autocomplete`, `inputmode`, and visible errors tied with `aria-describedby`.
- Images: meaningful `alt`, or `alt=""` for decorative ones. Icon buttons get `aria-label`. Footer and social links have text names.
- Modals (age gate, cookies, popups) are real dialogs: focus-trapped, keyboard-dismissible, with clearly named buttons. The content under them stays in the HTML for crawlers.
- Stable `id`s or `data-testid`s on key elements: search, price, add-to-cart, quantity, nav, primary CTA.
- Price, availability, and key facts are DOM text, never baked into images or canvas.
- No infinite scroll without paginated links, and no JS-only tabs without a fallback.
- Respect `prefers-reduced-motion`. Don't let animations hide content from the accessibility tree.
- axe-core: zero serious or critical violations.

## 6. Bot access at the edge
- Check the CDN/WAF (Cloudflare, Vercel, Medusa Cloud, etc.) for "block AI bots", bot-fight modes, or challenge pages. Agent files and public pages must be reachable by the allowed crawlers.
- Verify with curl using real user-agent strings (GPTBot, ClaudeBot, PerplexityBot, OAI-SearchBot, Applebot) and confirm each gets 200 plus real HTML, not a challenge page.
- If analytics exist, make sure AI/bot traffic is labeled rather than dropped, so the owner can see agent visits.

## 7. Verification (must pass before saying done)
Add these as scripts and wire them into CI or the build where possible:
- The build succeeds; serve the production build locally.
- Crawl every route: every page returns 200, no broken internal links, every sitemap URL returns 200, and no sitemap URL is Disallowed.
- JSON-LD validates against schema.org shapes and matches visible content.
- Lighthouse (mobile) on key pages: SEO 100, Accessibility 95+, Best Practices 95+, Performance 90+.
- axe-core: zero serious or critical issues.
- curl `/robots.txt`, `/llms.txt`, `/llms-full.txt`, sitemaps, feeds, and `.md` twins: check status, content-type, and content.
- curl key pages with no JS: main content, prices, and headings are present in raw HTML.
- Bot user-agent curl checks from section 6.
- Safari 27 smoke (on a Mac with Safari 27 and Remote Automation enabled; use `safaridriver --mcp`): open a tab, load home, a category, and a product/service page; read the accessibility tree; confirm the h1, price, availability, and a named primary CTA are present; confirm any age gate is a named dialog the agent can dismiss; no console errors. Browse only: no checkout, sign-up, or form submits.
- Visual diff against the baseline screenshots: no visible design changes beyond accessibility fixes.

## 8.5 ARI-100 — the merged scoring instrument (2026-11-09)

Five public scoring instruments were reversed to their check lists, weights and scoring semantics and merged into one registry that is a strict superset of all of them. It ships in this skill; nothing here is a rewrite of sections 0-8, it is the measurement layer that tells you what to fix first and proves the fix landed.

### Run it

```bash
cd <your-ops-dir>/shared-skills/ai-discoverability-max
node scripts/agentkit/cli.mjs https://<host> --json /tmp/r.json --md /tmp/r.md
```

Output: ARI-100 (0-100), grade A+..F, level L0-L5, a crawler reachability matrix (one live request per bot identity), a separate accessibility sub-score, and every failing check with observed evidence plus a copy-paste fix prompt, ranked by recoverable points.

### The eight domains and why the weights are what they are

| domain | weight | what it decides |
|---|---|---|
| Reachability & Access | 20 | can the crawler that cites you even get in (live probe, not the file) |
| Render & Delivery | 10 | does the text exist before JavaScript runs |
| Structure & Semantics | 12 | can an agent extract a passage: title, H1, canonical, landmarks, control names |
| Structured Data | 12 | are the facts declared rather than inferred |
| Discovery Files | 14 | llms.txt, sitemaps, markdown mirror + negotiation, AGENTS.md, Link headers, DNS, content-signals |
| Agent Interfaces | 14 | OpenAPI, API catalog, MCP card + live endpoint, A2A card, auth.md, scopes, problem-details, rate limits |
| Operability & Commerce | 10 | real controls, price/stock/variants in HTML, commerce profile, cart permalinks |
| Trust & Authority | 8 | author, dates, sources, entity consistency, HTTPS, headers |

Full list with per-check weights, tiers, pass criteria and fix prompts: `references/ari-100-registry.md`. Scoring math, gating and limits: `references/ari-100-scoring.md`. What each source family contributed and what was deliberately rejected: `references/ari-100-synthesis.md`.

### Non-negotiable interpretation rules

1. **Null is not zero.** A check that could not run or does not apply is excluded, never failed. A brochure site is not punished for having no checkout; a site behind identity-verified bot rules is not punished for a test one server cannot perform.
2. **Applicability by evidence.** The interfaces domain only scores when a developer surface exists. The commerce checks only score when commerce exists. Do not report a gated domain as a failure.
3. **Essential first.** When choosing work, take failed `essential` checks before any `recommended` gap. The essentials are what an ordinary agent needs.
4. **Rank by recoverable points**, not by count. One weight-5 essential beats five weight-1 optionals.
5. **Bonus never subtracts.** Emerging protocols add up to +5; their absence is not a defect.
6. **A11y under 80 caps the grade at A.** Agents read the accessibility tree; an unlabelled button is not an action.

### Procedure (baseline -> kit -> rescan)

1. **Baseline.** Run the scanner on the live host, save JSON. Quote the number in the card; never estimate it.
2. **Gap list.** Take `fixes[]` in order. Each has `id`, `evidence`, `recoverable`, `prompt`. That list IS the spec for the build card — do not re-derive it by hand.
3. **Publish the static kit.** Most discovery/interface gaps are pure files, no backend:
   ```bash
   node scripts/agentkit/kit.mjs sites/<site>.json out/kit-<site>
   ```
   Emits `robots.txt` (named AI groups + Content-Signal + Sitemap), `llms.txt`, `llms-full.txt`, `AGENTS.md`, `auth.md`, a `sitemap.xml` **index** with segmented children under `/sitemaps/` (pages, products, docs — an index survives catalog growth past the 50k-URL cap and the segmented check is worth 2 points), the whole `.well-known/` set (mcp.json, agent-card.json, ard.json, api-catalog, ai-catalog.json, oauth-protected-resource, oauth-authorization-server, agent-skills/index.json, and ucp/x402/acp when `commerce: true`), plus `head-snippet.html` and a README listing the response headers to add. Merge, never blind-overwrite an existing robots.txt that already names its bots.
4. **Rescan the same host** and quote the delta. A fix without a rescan is unproven.
5. **Report.** Baseline number, closing number, the checks that closed, the checks that remain and why.

### Known limits to state in any report

- One vantage point: probes come from this machine, not from each operator's IP ranges. A rule keyed on verified identity reads `unverifiable` and is excluded — never reported as blocked.
- A snapshot of one URL at one time.
- Deterministic extractors, not a DOM engine; a tool registered in unreadable code is missed.
- Two sampled inner pages and one representative detail page stand in for a template.
- The score says nothing about security, legal compliance or content quality.

### Where this is heading

The same registry backs a public service (<product>) — a free scan, a paid remediation report, a badge, and an MCP endpoint so an agent can call the checker directly. A your orchestrator plugin wraps that MCP endpoint as two tools: score a URL, and get the ordered fix pack. Keep the registry as the single source of truth; the site, the plugin and this skill all read it.

**A name you invent for that service is a decision, not a detail.** Within an hour of choosing one it is in a repo directory, a plugin id, a Worker name, a catalog entry, a PR title and a submitted form — and renaming it afterwards means resubmitting the form. Surface the name to the owner in the same message where you first ship anything under it, or ask before the first artifact lands; do not let him discover it from a URL.

# Operating layer (your orchestrator)

## How to report a decision to the owner

When he asks *why* you chose something (a branch, a host, a tool), answer in this
order and stop: **context** (what the artifact actually is, with the numbers that
make it non-obvious), **recommendation** (one option, named), **rationale**,
**risk if you do it**, **risk if you do not**. He reads a comparison table as
evasion — pick one and say why.

When he asks *what to do*, give **exactly ONE step**, imperative, with the literal
command. Not a plan, not a numbered list of five, not options. Say what the step
achieves in one clause, run it, report what came back, then give the next one. A
five-step plan is a menu; he will tell you to move the ball forward.

Corollary for blocking questions: a "blocker" that is really *my* automation limit
must be phrased as such. "Funnel needs a policy click" is an owner action; "the
tool does not work" is a false claim that burns his trust in the diagnosis.

Corollary for capability claims: "it files at all N for sure" is a measurement, not a
design statement. Probe every target from the vantage the product would actually run
from and classify each one's wall (no wall / JS challenge / captcha / phone or ID check /
dead domain / needs the user's mailbox), then quote the buckets. A status from a single
HTTP client is a fingerprint result, and the same page can be both "403" and "fillable"
depending on who fetches it. Walking back a coverage number after he has repeated it is
worse than quoting a smaller, measured one.

## Procedure (everything up to dispatch happens in ONE turn)
1. **Dedupe inventory.** `python3 scripts/dedupe_inventory.py <ws>/dedupe-inventory.json`: every task-tracker issue, task card (21 d) and PR (both repos) on AEO/SEO/JSON-LD/llms/sitemap/robots/Safari/MCP/a11y/speed. Read non-Done rows. Prior read-only audits live under `docs/research/` on main; point builders at them, never re-audit.
2. **Measure live.** `python3 scripts/site_audit.py https://<host> --out <ws>/audit` per site (signed-out GETs, 2 req/s). Covers brief sections 1/2/4/5 statically: robots per bot (18), sitemap union + same-lastmod count + image entries, sitemap-URLs-Disallowed, llms files, .well-known, feeds + md twins (flags SOFT-200 catch-alls), real 404, /version, security headers, per page: title/desc/canonical/h1 FLAGS, og:site_name/type/locale/url, twitter, JSON-LD types, landmarks, img-without-alt, clickable divs, heading skips, WebMCP, GPTBot parity. Lighthouse, axe and JSON-LD-vs-visible matching need a build, so they are BUILDER gates.
3. **Gap list = standard section by section, minus live-good, minus done/in-flight work, minus holds.** Each row: brief section #, live evidence (URL + observed value), fix. A gap an open card owns gets a comment there. An open issue the scorecard shows fixed closes as OBE with evidence.
4. **Dispatch one fix card per site** (cc, ENGINE <your coding agent>, ONE PR). Spec `<ws>/spec-<site>.md` holds the gap table, report paths, overrides + holds verbatim, `Doctrine: references/standard.md (v1.1)` and DONE-MEANS = section-6 gates below. Copy the spec to `<your-ops-dir>/tasks/workspaces/<task_id>/SPEC-aidisc-<site>.md` right after creating the card (else card-custody flags SPEC MISSING). If a fix card for the site is already open, the new card is a STACKED follow-up: `parents=[<open card>]`, branch from that PR head, so the two never fight over the SEO component. Plus ONE read-only Safari 27 smoke card on all prod hosts (body says 'never request_review'). Follow your task tracker's card-writing conventions before writing cards.
5. **Ship.** AR (<your reviewer model>, checks no-cloaking + JSON-LD == visible + zero visual change) -> your orchestrator merges -> release -> re-run `site_audit.py` on PRODUCTION and quote the closed rows. the owner inspects on production, never a local preview (<store> previews are sign-in gated).
6. **Promise ledger** row per site; the check curls the live host (`<your-ops-dir>/scripts/checks/aidisc-<site>-live.sh` pattern), never PR or card state. Prove each new check FAILS before the fix ships: `bash <check>; rc=$?; echo rc=$rc`. Never `echo "$(basename $f) rc=$?"`: the command substitution resets `$?` to 0 and fakes "already live" (10-11).

If a production build runs a gate script that fetches the backend, a local build without Cloud env needs a local stub answering that endpoint. If a test walks `src/app` against a route table, adding a route means adding the literal to every route list the tests compare.

## RFC 9727 API Catalog linkset (publishing + independent review)

### Verify the href before chasing the header (2026-11-05)
<store> lost hours trying to emit `Link: <https://<store>.example/api/catalog>; rel="ai-catalog"`. That href returns **404** — the catalog is served at `/.well-known/api-catalog` (RFC 9727 linkset, live, 200), and the registered relation is **`api-catalog`**, not `ai-catalog`. Rule: `curl` the href first; if it is not 200, the discovery work is to publish the resource, not to emit a pointer to nothing.

### Next.js overwrites the `Link` header — do not try to merge into it
Next emits its font/CSS preloads as one `Link` header with N comma-separated entries, written with `set`. Measured on OpenNext 4.1.8 for the same route: middleware `append` -> preloads `0`, extra entry `1`; `next.config` `headers()` `Link` -> preloads `7`, extra entry `0`. There is no ordering that yields both.

Therefore: publish the discovery pointer as an HTML `<link rel="api-catalog" href="/.well-known/api-catalog">` in the document head (framework-safe, once per document, zero preload risk), and treat the HTTP `Link` variant as a known framework limitation — never as a reason to ship a preload regression. If a page already emits that tag, move it into the root head; the diff must delete the old copy, because a second tag fails the exactly-once gate. Acceptance is served HTML from `next build && next start`, not a source grep: document routes contain the tag once, admin / api / static / `_next` contain zero, and the `Link` header's preload count is byte-identical to before.
When a site must publish `/.well-known/api-catalog` (RFC 9727 / RFC 9264 linkset) or you are the INDEPENDENT reviewer of such a change, use `references/rfc9727-api-catalog-linkset-recipe.md`. It carries the body shape (relation values are arrays of `{href,type}`, `anchor` required), the rule that `service-desc` is a RELATION TYPE and may point at the MCP server card (not only at OpenAPI) with a negative test that no OpenAPI relation is invented, the "every href must answer 200 signed out today" gate, the dotted-root-path `ROOT_FILES` + middleware-before-the-wall trap, gate-flag coupling, origin derivation from the app's own helper cross-checked against the live MCP card, HEAD+GET reachability, and the reviewer's evidence list + verdict shape.

## Serving the site to a bot over MCP (the `/mcp` endpoint)

WebMCP (`navigator.modelContext`) only reaches agents sitting in that browser tab. A bot — Grok Bot, an agent loop, any third-party client — needs a public `/mcp` endpoint. Same standard, different transport, and it is a smaller job than it looks because the agent-read layer already exists.

- **Probe a sibling store's live endpoint before designing your own.** <store> runs a read-only `/mcp` (`list_products`, `get_product`, `get_policies`) whose every tool description carries the site's own "not for human consumption" notice. Reuse that shape — a flat read-only inventory, no mutations — so every store speaks the same contract and a bot can be pointed at more than one of them. The sibling is also how you spot the split shape: if one store's `/.well-known/mcp.json` lists its tools top-level and another store's only carries them in a vendor-namespaced `_meta` block, that divergence IS the defect, and the sibling is the reference implementation. Read the sibling's actual live card, never your memory of it.
- **Host it on the Worker/route that already serves the site.** A publicly reachable endpoint needs no tunnel at all. Reach for a tunnel only when the server is local, and then know the constraint before you pick a provider: Cloudflare quick tunnels do not carry SSE, so an SSE-transport server needs ngrok or a real tunnel, while Streamable HTTP works fine through Cloudflare.
- **A published endpoint is a contract, so nothing that consumes it may hardcode a host that must already exist.** A quick tunnel dies with the process, which means every README, catalog entry and plugin default pointing at it rots silently and the failure lands on whoever installs next. Two habits fix this: host the service somewhere durable (a Worker on `*.workers.dev` needs no domain and no new credential when wrangler is already authenticated), and make the CLIENT resolve at runtime — an ordered candidate list probed once with a short timeout, the winner cached for the process, and an explicit env/setting override still winning. Prove it the way a stranger experiences it: fresh clone, empty environment, one call, real result.
- **Pick the transport shape from the platform's current table, not from a tutorial.** Cloudflare's Agents docs compare stateless vs stateful handler options explicitly and have deprecated the stateful Durable-Object path for new servers; a read-only catalog server wants the stateless one.
- **Read-only public data needs no auth, and that is the correct v1.** Adding OAuth changes the product posture, not just the code — it is an owner decision, not a builder default. Keep the endpoint honest about capability instead: never expose a mutating tool the site does not have.
- **Three build-time traps decide whether the endpoint works; check them before writing the card.** (a) The site's data modules usually reach the filesystem at module scope, which does not exist in the Worker runtime — reuse the build's own `env.ASSETS` pattern instead of importing them. (b) A stateless handler's default hostname allowlist covers localhost and `workers.dev` only, so a custom domain needs the hostname named explicitly or production 403s. (c) A new `/mcp` path must be dispatched BEFORE any existing `/api/` catch-all and before content negotiation, or both swallow it. Full recipes and the exact commands: `references/mcp-endpoint-build-and-bot-wiring.md` §4.
- **A bot template does NOT carry MCP connectors.** The template ships identity, description, skills and routines; the person installing it adds the connector themselves. Put the connector URL and the exact add-it steps at the TOP of any template's setup section, or the recipient installs a bot with no tools and calls it broken.
- **Do not build a voice pipeline the host app already ships.** Before scoping STT/TTS, confirm what the bot platform does natively — if it already has live voice chat, dictation and voice memos, that requirement is met. Spend the effort on what actually gets spoken: tool descriptions, and a guidance tool that carries the site's rules so they are enforced at the record level rather than only in prose.
- **A bot voice is us speaking.** Anything the bot relays is on the brand, including a skeptical third-party quote it found in a cited source. Put the attribution rule in the bot instructions: attribute to the source's link, never to the site. **Do NOT also tell the bot to suppress, avoid or soften a source's own caveat** — see `references/mcp-endpoint-build-and-bot-wiring.md` §3 for why suppressing a doubt makes an attribution-only site start making claims. Also audit the template as an instruction set before it ships (`/bitterpillengineering`), which is what catches this rule. See `do-not-act-retarded` rule 1.

Depth: `references/mcp-endpoint-build-and-bot-wiring.md` — tool inventory, the notice/attribution contract, and the connector-vs-template split. `references/mcp-server-card-parity.md` — making the discovery card list the tools the endpoint serves. `references/external-agent-readiness-score-recipe.md` — when the acceptance target is a NAMED third-party agent-readiness scanner's score: read the scanner's own published rubric, reproduce every check locally before building, never advertise an endpoint that 404s, split auth into its own card, and keep DNS-only checks on the ship card.

## When the site is a client-rendered SPA (Vite/React on a Worker)

- **An empty mount node is the whole score.** A bare SPA reads ~65/100 (grade C) with Render & Delivery at 40%: a thin HTML shell, no text, no H1, no landmarks. Server-render per route BEFORE touching discovery files — measured on one build it moved 65 → 88 with Render & Delivery at 100%, and it is the cheapest large win on this class of site.
- **Prerender in the host, not in a framework.** A Worker that already serves the assets injects route-specific HTML into the mount node from ONE `pageMeta(path)` switch (title, description, body string), reusing the app's own class names so a JS-enabled visitor sees no flash. `createRoot().render()` replaces prerendered children; `hydrateRoot` on string-rendered markup does not — pick one and stay with it.
- **The router must know its own pages.** An assets layer with `not_found_handling: single-page-application` answers EVERY unknown path with the shell at 200 (soft 404). Keep an explicit `KNOWN_PATHS` set, serve the prerendered page for it, and return a real 404 body plus status for everything else.
- **Static routes need not ship JS at all.** A search page or an about page built from a native `GET` form and real links can skip the client mount, which keeps the server's output authoritative and the page working without a bundle.
- **Edge-cached HTML hides a deploy.** `cache-control: max-age=60` on a page means curl AND the browser show the previous build after `wrangler deploy`, and the "change didn't land" hunt is wasted time. Serve pages `public, max-age=0, must-revalidate`, verify with `?cb=$RANDOM` plus `-H 'cache-control: no-cache'`, and bind `/version` to the Worker's `version_metadata` so the live build id is a fact.
- **Scanners probe both spellings.** Publish `/openapi.json` AND `/.well-known/openapi.json`, `/AGENTS.md` and `/agents.md`; put `Link: rel="alternate"` / `rel="service-desc"` and `Content-Signal` on the HTML response for GET *and* HEAD.
- **A `<noscript>` heading duplicates the prerendered H1** and fails the one-H1 check; use plain text there.
- **Per-page JSON-LD has to ride the same injection.** The shell's static `@graph` can only describe what is true of every route (`Organization`, `WebSite`), so a route that earns `Article`, `FAQPage` or `BreadcrumbList` needs its graph appended by the Worker next to the injected body. Emit it from the module that also renders the visible FAQ, so markup and claims cannot drift when a question is edited.

Full recipe (injection point, header set, PBKDF2 and cron traps, verification battery): `references/spa-to-agent-ready-prerender.md`.

## Third-party audit triage variant (an EXTERNAL scanner hands you a fix list)

A different lane from everything above: an outside agent-readiness/SEO scanner produces a fix list for our sites and it reaches us RELAYED (another bot, another machine, a shared-box markdown file). None of the normal dedupe → measure → dispatch flow applies, because the artifact is not on our disk and the claims are about LIVE production, not a PR head.

**Do not convert a relayed fix list into cards. Grade every row against live first.** The list is a set of claims about production, and claims about production are the one input most likely to be stale, already fixed, or wrong in a way that matters.

1. **Confirm the artifact is actually readable before you cite it.** A relayed path (shared box, another host, a bot's mount) usually does not exist on this machine. If the file is not readable here, say so plainly and work from the summary you were given — never imply you read the full document when you read a relay of it.
2. **Grade every row into exactly one bucket, with live evidence:**
   - `CONFIRMED` — reproduced against production, quoted with the command and its output.
   - `ALREADY-FIXED` — the surface exists and is correct (a `200` where the audit claims `404`).
   - `FALSE_POSITIVE` — the opposite of the claim, also with live evidence.
   - `UNVERIFIED` — you could not reproduce it either way. **This bucket is not optional.** A row you could not confirm is not a gap and must never be reported as one; it becomes a code-read or a load test inside the card instead.
3. **A claim you cannot reproduce at low volume is usually under-powered, not absent.** Three fast calls all returning `200` says nothing about whether a rate limiter exists — it says the limiter's threshold is higher than three. Report the limit as UNVERIFIED and put "find the threshold by reading the limiter config / a real burst test" into the card.
4. **Verify the claim's SCOPE, not just its truth.** An audit row that says "X is missing" may be half right: the missing half and the present half are separate findings with separate fixes. Check each named element individually and report which ones are genuinely absent.
5. **Sort the graded list by blast radius, not by the audit's numbering.** Money-movement and payment defects outrank discoverability polish regardless of where the scanner put them. State that reordering explicitly so the operator sees why item 5 shipped first.

**The one question that is never yours to answer.** When an audit row is really a business fact ("is the store open?", "should this trade-only catalog be crawlable?", "may this research-use-only site take payments through an agent?"), the row is flagged to the owner with a recommendation and a confidence percentage. You do not resolve it, and you do not quietly pick the reading that lets the card ship. A contradiction between a human-facing surface and an agent-facing surface means exactly one of them is wrong, and only the owner knows which — that is the highest-value row in the whole list and it goes first in the report.

## Scripts
- `scripts/agentkit/cli.mjs <url> [--json f] [--md f]`: **ARI-100 scanner** — 120 checks, 8 weighted domains, 32-crawler live reachability matrix, accessibility sub-score, and a ranked fix list with a copy-paste prompt per check. Deterministic, no browser, no model in the scoring path. This is the measurement layer for §8.5.
- **Three traps when you project a kit-applied score.** (a) `preview.mjs` is a local self-signed TLS proxy: the projected scan dies at the handshake unless `NODE_TLS_REJECT_UNAUTHORIZED=0` is set IN-PROCESS before the scan, and the failure surfaces as `projected: null` with an EMPTY error string — a null projection is a TLS problem until proven otherwise, never "no kit benefit". (b) Regenerate every kit (`node scripts/agentkit/kit.mjs <cfg> out/kit-<host>`) before benching; a stale kit directory under-reports, because the proxy 404s any file the old kit never wrote. (c) **Adding a check lowers every score.** A superset index is only comparable within one registry version: after registering new checks, re-baseline all sites and publish both numbers with the check count named, or the delta reads as regression instead of an instrument getting stricter.
- **Three false-negative traps this scorer already hit — audit any new check against them.** (1) *Truncation*: if a check reads a sampled/`slice(0, N)` link list, a footer link on a page with 300 anchors reads absent. Checks that ask "does the site link X" must read the full deduped set; only the inner-page fetch may be capped. (2) *Accessible name precedence*: `<label for=id>` and a wrapping `<label>` come BEFORE `aria-label` in the accname spec, and an `id` alone is not a name. A bare `alt` means `alt=""` (correct for decorative images), so `/<img[^>]*\balt\b/` is presence and `\balt\s*=` is not. (3) *Filename case*: the spec names the skill file `agents.md` in lower case, and a production server is case-sensitive, so probing only `/AGENTS.md` docks a site that publishes `/agents.md` correctly. Probe every spelling the spec and the ecosystem use (`/AGENTS.md` -> `/agents.md` -> `/.well-known/agents.md`) before calling the file missing. Every one of these made a real site read 1-6 points low while the site was fine — before you write a fix card off a single missing-file finding, confirm by hand that the file is not simply somewhere the checker did not look.
- `scripts/agentkit/kit.mjs sites/<site>.json <outDir>`: emits the static readiness kit (robots.txt with named AI groups + Content-Signal, llms.txt, llms-full.txt, AGENTS.md, auth.md, sitemap.xml, the full `.well-known/` set, head snippet, and the response headers to add) from one config object.
